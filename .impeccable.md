# Impeccable — Verdaxis Frontend

## Scope
This file governs the entire Verdaxis frontend:
- public site
- authenticated application
- shared primitives, tokens, copy tone, and interaction patterns

Feature-level design docs may add local rules, but they must not conflict with this file.

## Product Character
Verdaxis should feel like a serious green-fuels market product, not a generic SaaS dashboard and not a consumer marketplace.

Core traits:
- credible
- operator-grade
- market-aware
- precise
- restrained

The interface should suggest execution confidence, market structure, and real commercial context.

## Experience Split
### Public site
- Slightly more atmospheric and narrative.
- Used to build trust, explain the market, and position Verdaxis as an intelligent market venue.
- Can use stronger visual storytelling, but should still feel industrial and credible rather than glossy startup-marketing generic.

### Authenticated app
- Denser, faster, and more operational.
- Optimized for scanning, comparing, filtering, and acting.
- Should feel like a modern market console, not a consumer feed.

Shared rule:
- both surfaces must feel like the same company and the same product family

## Visual Tone
- Prefer maritime, commodities, logistics, and energy seriousness over fintech flash.
- Use calm neutrals, disciplined accents, and clear state colors.
- Avoid loud gradients, decorative glows, and novelty styling unless a page has a specific justified concept.
- Avoid default AI-dashboard aesthetics.

## Typography
- Typography should feel controlled and high-signal.
- No generic safe-SaaS typography decisions by default.
- Dense operational text is acceptable, but supporting copy should remain readable.
- Do not push supporting UI copy below 11px unless there is a strong reason.
- Numbers, prices, quantities, and benchmark deltas should read with strong tabular clarity.

## Layout And Density
- Use a disciplined 8px spacing system.
- Favor structured density over oversized cards and wasted space.
- Dense does not mean cramped: hierarchy must still be obvious.
- Tables, ladders, and lists should prioritize scan speed.
- Filters, tabs, summaries, and tables must read as one coherent system, not separate design islands.

## Controls
- Do not ship browser-default-looking controls on core product surfaces.
- Shared inputs of the same level should look like they belong to the same family.
- Avoid mixing interaction grammars in one toolbar without a strong reason.
- If a filter is visible, the user should understand whether it applies immediately or requires a commit action.
- Prefer immediate, legible filter behavior over hidden or surprising state.

## Market Surface Rules
- Market structure must be obvious.
- Metrics must declare their scope.
- Aggregate counts and selected-slice counts must not be visually conflated.
- Critical market actions must use explicit market language.
- If a view is executable, labels must reflect execution semantics.
- If a view is observational, labels must not imply execution.

## Data Visibility
- Important qualification data must be easy to scan before action.
- Hover may enhance detail, but must not become the only path for understanding a row on touch-heavy workflows.
- Empty states should distinguish between:
  - no data exists
  - no results match current filters
  - the user needs to make a selection first

## Motion
- Motion should be purposeful and restrained.
- Prefer short, useful transitions.
- Avoid decorative looping motion.
- Motion should clarify hierarchy, reveal state, or reinforce interaction feedback.
- Respect reduced-motion expectations.

## Copy Tone
- Clear, commercial, and direct.
- Avoid consumer-language metaphors unless explicitly approved.
- Avoid vague feature branding when plain language is clearer.
- Status labels and button text should match the actual system behavior exactly.

## Responsiveness
- Mobile and tablet layouts should preserve the same mental model as desktop.
- Do not let breakpoint changes invent new interaction models unless intentionally designed.
- Filters, tabs, and key actions should remain understandable at narrow widths.

## Anti-Patterns
- No purple-on-white AI SaaS look.
- No generic glassmorphism as a default style.
- No consumer social metaphors for market workflows unless explicitly requested.
- No fragmented filter bars with mixed styling and hidden logic.
- No ambiguous metric cards that combine different scopes.
- No empty whitespace-heavy dashboard filler.
- No decorative charts, maps, or motion without decision-making value.

## Definition Of Done For Frontend Changes
- The change matches this file and any relevant feature-level design doc.
- The interaction language matches actual backend behavior.
- Metrics and counts are scoped clearly.
- Responsive behavior preserves the same mental model.
- The result avoids default-looking controls and generic AI UI patterns.
- If a change introduces a new reusable visual pattern, update the relevant design doc in the same commit.
