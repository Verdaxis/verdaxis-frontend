# B100 shared orderbook implementation plan

**Goal:** Make B100 use the existing orderbook, trading lifecycle, Map and forward curve, with fuel-specific specifications.

**Architecture:** Extend existing BID/ASK contracts and immutable trade snapshots with validated B100 terms. Use the existing matching, direct-taking, negotiation, inventory and market-data paths. Keep prior indicative offers and requests as history; never turn them into standing orders without a new explicit submission.

**Tech Stack:** React/TypeScript, FastAPI/Pydantic, SQLAlchemy, PostgreSQL/Alembic.

The user approved this design on 22 September 2026 after correcting the earlier RFQ-only implementation. No additional design approval is required. Deployment scope is staging only.

## Implementation and ownership

1. Backend contract and execution: add typed B100 order data with distinct buyer requirements and supplier declarations. Check standard/edition/grade, cold-flow limits, carbon basis, certification and delivery terms. Use the same compatibility policy in automatic and explicit execution. Preserve quantity locks, provenance, permissions and private evidence. Tests must show compatible fills and incompatible rejections before implementation.
2. Catalog and schema: change UCOME execution mode to ORDERBOOK; retain the approved Singapore lane. Add a new migration after supplier offers, exact runtime ACL grants, database guards and immutable trade terms. Preserve prior orders, quotes and supplier offers. Test migration/checkpoint and runtime-role boundaries.
3. Shared UI: B100 selects ordinary Listings/Orderbook/My Listings and the standard BID/ASK modal. Retain fuel-specific fields and show submitted terms before execution. Preserve prior RFQ/offers in clearly named history access. Update API types, safe response mapping, English and Chinese copy.
4. Market data: include B100 in Map, ticker and forward curve, with real order/trade/indication provenance and honest empty states. Only supported product/port pairs are offered. Do not fabricate prices, use assumed heating values, or convert legacy indicative offers into liquidity.
5. Verification: focused regressions, full frontend suite/typecheck/i18n/build, backend unit and PostgreSQL suites, adversarial source review and disposable browser supplier/buyer flow. Verify matched trade snapshots, rejected incompatible requests, cancellation and old alcohol paths.
6. Release: commit exact reviewed source to staging, verify CI, fresh attested backup, deploy through the guarded checkpoint and verified frontend artifact. Verify live readiness, B100 orderbook/Map/curve, and production fingerprints.

## Acceptance

B100 has the same executable workflow as the other fuels. Industry fields remain visible and survive order/trade readback. Wrong specifications cannot execute through an alternate endpoint. Forward curve includes B100 even when it has no price observations. Existing indicative offers retain their original meaning. Production is unchanged.
